# wenia-platform-workflows

Reusable GitHub Actions workflows for services generated by the Wenia IDP.

Generated services call these workflows and pin to `@v1`. A fix here reaches every service without regenerating them — this is the template evolution mechanism described in the Wenia IDP upgrade strategy.

## Workflows

| Workflow | Trigger | What it does |
| --- | --- | --- |
| `ci.yml` | `workflow_call` | Tests, secrets scan, dependency audit, image build (no push) |
| `cd.yml` | `workflow_call` | Builds and pushes image to GHCR; deploys only when `DEPLOY_ENABLED=true` |

## How generated services call these

In `.github/workflows/ci.yml` of a generated service:

```yaml
jobs:
  ci:
    uses: <your-github-username>/wenia-platform-workflows/.github/workflows/ci.yml@v1
    with:
      service-name: my-service
      language: nodejs
      node-version: '22'
```

## Inputs

### ci.yml

| Input | Required | Default | Description |
| --- | --- | --- | --- |
| `service-name` | yes | — | Used for the image tag |
| `language` | yes | — | `nodejs` or `python` |
| `node-version` | no | `22` | Node.js version (nodejs only) |

### cd.yml

| Input | Required | Default | Description |
| --- | --- | --- | --- |
| `service-name` | yes | — | Service name |
| `language` | yes | — | `nodejs` or `python` |
| `node-version` | no | `22` | Node.js version |
| `image-registry` | no | `ghcr.io` | Container registry |

## Versioning

- Tag `v1` is the stable pin. Backwards-compatible fixes are applied to `v1` by moving the tag.
- Breaking changes get a new major tag (`v2`).
- Generated services reference `@v1` in their workflow files.

## Repository requirements

- This repo must be **public** so generated repos (also public) can call its workflows.
- The `v1` tag must exist before the first service is generated — CI will fail otherwise.
